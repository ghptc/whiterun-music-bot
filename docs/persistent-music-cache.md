# Persistent music catalog (CR-002)

The catalog uses the existing SQLite file and WAL configuration, shared across guilds. Migration 003 adds `music_catalog(spotify_id PRIMARY KEY, metadata JSON, updated_at)` and an expiration index on **existing** `mappings`. It neither copies nor replaces mapping evidence. Existing `tracks`, queue/history and settings data remain compatible.

Spotify catalog records whitelist original title, artists, album, duration, ISRC, explicit marker and safe artwork URLs. They exclude requester, collection position, guild, session and signed stream URLs. Candidate JSON in `mappings` already stores the validated YouTube ID, thumbnail, availability, identity evidence and `bard_checked_at`; its policy/metadata fingerprint protects Spotify Fidelity. No audio, image BLOB, Redis or additional memory cache is introduced.

For a Spotify track URL, `/play` reads metadata by Spotify Track ID before contacting Spotify. A metadata hit within 24 hours bypasses the Spotify metadata request. Album/playlist membership is still obtained from Spotify, because it can change; individual mappings are reused. Successful provider metadata retrieval refreshes the catalog. Merely playing cached metadata does **not** renew its freshness timestamp. On cache miss/expiry/read failure, the existing provider/resolver path continues.

Mappings retain their existing 24-hour database expiration and ten-minute identity/availability lease. A fresh confirmed candidate avoids search and full metadata extraction. After that lease, the exact video is re-extracted and compared against the original Spotify identity before reuse. Failure invalidates the locator; identity mismatch can enter normal discovery. Extraction errors fail that attempt closed and subsequent attempts no longer reuse the invalidated locator. Discovery still stops at the **first confirmed match**. Stream format extraction always checks actual access, even during a fresh lease.

Playback/identity failures invalidate both the existing in-memory search entry and persistent mapping; deliberate cancellation/skip does not. SQLite deletion compares the failed video ID atomically, protecting a newer replacement from an older failing stream. Cache operations have a 200 ms context budget and errors never replace a successful media resolution with a cache error. Parent request cancellation still applies. General availability can change between validation and streaming; no cache hit is permanent proof.

Upserts are atomic and identities unique. The database serializes its single connection with a three-second SQLite busy timeout; operation contexts impose the shorter cache budget. Guild queue/requester/session isolation continues through the existing guild-keyed durable state, separate from global catalog records. Expired catalog/mapping rows are ignored and overwritten on refresh; this change does not add background eviction.

Metadata queries measured 5.677 µs for hits and 3.769 µs for misses (`go test ./internal/storage -run '^$' -bench BenchmarkCatalogSQLite -benchtime=1s`). These results do not justify a new L1 cache. The preexisting search cache remains unchanged except for targeted invalidation after playback failures.

`catalog_lookup` and `spotify_mapping_lookup` log hit/miss, success and elapsed time. Derive hit rate as successful hits divided by successful lookups. `catalog_write`, `mapping_write_failed`, `mapping_read_failed` and `spotify_mapping_invalidated` expose storage health. Fresh mapping-hit events report minimum external searches/verifications avoided; catalog hits report avoided Spotify metadata calls. These counts cover observed hits, not estimated playlist/network behavior. Logs contain no credentials.

Tests use real SQLite files for restart, cross-guild reuse/isolation, concurrent upsert, expiration, invalid JSON/empty identity constraints and stale-stream conditional invalidation. `BARD_TEST_EXISTING_DB=/path/to/consistent/backup.db go test ./internal/storage -run TestExistingDatabaseUpgrade -v -count=1` validates migration/integrity on a temporary copy. Use a SQLite-consistent backup, including a checkpoint when copying an active WAL database; never point the bot at an unverified replacement of production data.

The container volume used for the acceptance copy upgraded successfully. Normal deployment applies the migration transactionally on startup. Roll back the binary only with an appropriate backup: older binaries intentionally reject newer database schema versions.
